# Спецификация OMR — Oh My Remotion

Статус: согласованная основа для реализации; допускает дальнейшие дополнения.
Источник: интервью с владельцем проекта в этой сессии OpenCode, 16 октября 2026 года.
Требования к публичному GitHub-репозиторию, MIT и документации добавлены
последующим прямым поручением владельца.

Этот документ передаёт решения между отдельными сессиями. Наличие требования
не означает, что соответствующая возможность уже реализована или проверена.
Порядок работ и отметки о выполнении находятся в [TODO.md](TODO.md).

<a id="scope"></a>
## 1. Назначение и границы

OMR — локальный набор скилов и команд OpenCode для создания видеороликов.
Процесс универсален: тема, жанр, цель, аудитория, длительность, формат,
визуальный стиль и звук определяются отдельно для каждого ролика.

Поддерживаются три режима:

1. **Remotion:** весь ролик реализуется в Remotion.
2. **Manim:** самостоятельный ролик реализуется в Manim Community Edition.
3. **Гибридный:** Manim рендерит анимационные фрагменты, а Remotion собирает
   итоговый ролик с остальными сценами, титрами и звуком.

Созданы четыре самостоятельных скила этапов и одноимённые slash-команды.
Дополнение по обсуждению с владельцем: единый ведущий `omr` с командой `/omr`
и независимый `omr-review` с `/omr-review`. Единый режим — рекомендуемый вход;
отдельные этапы остаются доступны для ручной работы и иной оркестрации.

<a id="publication"></a>
## 2. Публичный репозиторий и лицензия

- Первая задача реализации — создать публичный репозиторий проекта в GitHub
  владельца с MIT-лицензией для собственного кода и документации OMR.
- Рабочее имя проекта — `omr`. GitHub-аккаунт и точный адрес репозитория пока
  не установлены; их нужно определить перед публикацией, не выдумывая URL.
- Использовать `gh` для операций GitHub. Перед публикацией проверить весь
  состав публикуемых файлов, включая имеющиеся локальные RIS-скилы, их
  происхождение и условия распространения. MIT OMR не заменяет лицензии
  сторонних материалов и зависимостей.
- README должен кратко описывать возможности, состояние реализации,
  установку и содержать отдельный блок для AI-агентов по установке OMR
  и настройке `AGENTS.md`.
- Не публиковать персональные ролики и ресурсы автоматически как часть набора.

<a id="workspace"></a>
## 3. Рабочая область и выбор проекта

Текущая рабочая область: `/home/aleksei/plums/omr`.
Этот абсолютный путь — факт текущего окружения, а не путь для встраивания
в переносимые скилы или инструкции установки.

- Каждый ролик создаётся в отдельной подпапке рабочей области.
- В репозитории разработки OMR личные ролики размещаются в `projects/<имя>/`;
  весь `/projects/` исключается из Git и публикации. Публикуемые учебные примеры
  и проверки размещаются отдельно в `docs/checks/` по явному поручению.
  Для других рабочих областей структура проектов согласуется с владельцем.
- Общие скилы находятся в `.opencode/skills/`; команды — в локальной
  конфигурации `.opencode/` по поддерживаемому OpenCode формату.
- Обычный сценарий: пользователь запускает OpenCode в папке ролика;
  текущая папка определяет проект без обязательного аргумента пути.
- Если запуск выполнен в корне рабочей области, скил сначала помогает выбрать
  или создать подпапку. Не создавать ролик прямо в корне OMR.
- Папки роликов остаются в общем Git-дереве без собственных вложенных
  Git-репозиториев: это сохраняет поиск родительских скилов.
- Все команды установки, разработки и рендеринга выполняются в контексте
  соответствующего проекта, а не корня рабочей области.

Согласно документации OpenCode, поиск локальных скилов идёт от текущего
каталога вверх до корня Git-дерева. Обнаружение скилов и команд из подпапки
нужно проверить на целевой версии OpenCode, а не считать проверенным по документации.

<a id="layout"></a>
## 4. Структура проекта ролика

```text
<название-ролика>/
├── requirements.md
├── content/
│   ├── index.md
│   └── <тема>.md
├── script.md
├── public/
├── src/
│   ├── remotion/
│   └── manim/
├── renders/
└── out/
    └── video.mp4
```

- `requirements.md` — требования к ролику.
- `content/index.md` — обязательная точка входа в контент, список материалов
  и порядок чтения; создаётся даже при одном файле материалов.
- `content/<тема>.md` — один или несколько содержательных документов с источниками.
- `script.md` — сценарий реализации материала с учётом требований.
- `public/` — входные и подготовленные медиаресурсы.
- `src/remotion/` и `src/manim/` — исходники соответствующих движков.
- `renders/` — промежуточные рендеры, в том числе вставки Manim.
- `out/video.mp4` — готовое видео в любом из трёх режимов.

Это целевая структура, а не требование создавать все папки в начале работы.
Папки неиспользуемых движков не создаются. Конфигурационные файлы, манифесты
и lock-файлы добавляются внутри проекта по фактической необходимости.

<a id="workflow"></a>
## 5. Переходы, редактирование и недостаточные входы

- В отдельном режиме этапы запускаются вручную. В режиме `/omr` требования
  прорабатывает ведущий, контент, сценарий и производство — отдельные субагенты.
  Все существенные вопросы проходят через ведущего в основном диалоге.
- После каждого этапа, включая требования, отдельный субагент выполняет ревью.
  После первоначального ревью — до двух кругов исправлений с повторной проверкой.
  Оставшиеся существенные проблемы выносятся пользователю. Затем ведущий показывает
  результат этапа целиком, пути файлов и ждёт разрешения на следующий этап.
  Более подробные остановки — только по указанию пользователя.
- Запуск следующего этапа означает согласие использовать текущие материалы.
  Обязательные статусы «черновик / согласовано» и отдельные утверждения документов
  не требуются.
- После изменения предыдущих материалов пользователь сам поручает переделать
  или отредактировать нужный следующий результат.
- Учёт версий и устаревания не нужен. При сквозной правке ведущий объясняет
  затронутые этапы, получает разрешение вернуться к самому раннему из них и
  организует правки с ревью и остановками после каждого. Отдельная команда этапа
  зависимые результаты не обновляет.
- Каждый скил проверяет достаточность своих входных материалов. При существенных
  пробелах или противоречиях сообщает о них и задаёт необходимые уточнения.
- Если обязательный результат предыдущего этапа отсутствует или недостаточен,
  скил объясняет, чего не хватает, и предлагает соответствующую команду.
  Предыдущий этап самостоятельно не запускается.
- Пользователь может предоставить эквивалентные материалы самостоятельно.
  Важно их содержание и достаточность, а не обязательное прохождение всех команд.
- Повторный запуск по поручению пользователя поддерживает редактирование
  существующего результата и сохраняет не относящуюся к поручению работу.

### Ревью и продолжение единого диалога

- `omr-review` использует общий метод и профильные руководства в `references/`
  для требований, контента, сценария и производства. Артефакт не исправляет.
- Отчёты: `reviews/{requirements,content,script,render}.md`. Есть отчёт —
  исполнитель учитывает описанные проблемы; нет — нет прежних замечаний из ревью.
  Ревьюер при повторной проверке отмечает исправленное и сохраняет полезную историю.
  Версии, хеши и отдельный реестр не вводятся.
- Отдельные команды этапов не запускают ревью. Независимое ревью запускается
  ведущим или отдельно через `/omr-review`.
- Короткий `workflow.md` хранит место остановки, текущую просьбу и разрешение
  продолжить. `/omr` восстанавливает контекст по нему и фактическим материалам;
  при неоднозначности спрашивает, а не принимает наличие файлов за согласие.
- Правки готового видео обсуждаются в том же диалоге по общим правилам возврата.

<a id="requirements"></a>
## 6. `omr-requirements` / `/omr-requirements`

**Результат:** требования к конкретному ролику в `requirements.md`.

- Изучить запрос, предоставленные материалы и известные ответы.
- Использовать `ris-port-op-interview` для адаптивного интервью: по одному
  существенному вопросу, с учётом зависимостей решений; не повторять уже известное.
- Предлагать обоснованные варианты для неопределённых пунктов, отделяя
  предложения от принятых решений.
- Установить тему, цель, аудиторию, требования к содержанию, структуре, дизайну,
  длительности, формату, звуку и ограничениям настолько, насколько это нужно
  для следующих этапов. Это области обсуждения, а не фиксированная анкета.
- Рекомендовать Remotion, Manim или гибрид и согласовать выбор с пользователем.
- Если нужна озвучка, определить способ её получения и голос. Зафиксировать
  существенные требования к остальным ресурсам.
- Завершить, когда требований достаточно для сбора контента и дальнейшего
  производства; сохранить документ как результат предметного скила.
- На этом этапе не устанавливать движки.

Скил владеет результатом `requirements.md`, а `ris-port-op-interview` — методом
интервью. Их нужно соединить в один диалог, без второго интервью или автоматического
перехода к сбору контента.

<a id="content"></a>
## 7. `omr-content` / `/omr-content`

**Вход:** достаточные требования и предоставленные пользователем материалы, если есть.
**Результат:** структурированные материалы в `content/` и обязательный `index.md`.

- Использовать материалы пользователя и самостоятельно искать внешнюю информацию
  по теме и требованиям.
- Собирать факты, объяснения и примеры; сохранять ссылки на источники найденных фактов.
- Организовать один или несколько Markdown-файлов и указатель с порядком чтения.
- Не подменять этот результат окончательным повествованием, текстом озвучки
  или последовательностью сцен: это ответственность сценария.
- Конкретные производственные медиафайлы не требуется заранее создавать
  или скачивать; ранее предоставленные ресурсы доступны всем этапам.
- Не устанавливать движки и не запускать следующий этап автоматически.

<a id="script"></a>
## 8. `omr-script` / `/omr-script`

**Вход:** требования, индекс контента и достаточные материалы.
**Результат:** сценарий в `script.md`.

- Отобрать материал и организовать его в сцены.
- Описать тайминг, экранные тексты, текст озвучки при её наличии,
  визуальные действия, звук и необходимые ресурсы.
- Определить реализацию сцен в рамках согласованного режима. Для гибрида
  обозначить, какие фрагменты создаются Manim и как включаются в Remotion.
- Учитывать длительность, разрешение, FPS и фон при стыковке фрагментов.
- Если для результата требуется сменить режим, обсудить это с пользователем,
  а не менять принятое решение молча.
- Сценарий должен позволять реализовать ролик без самостоятельного придумывания
  исполнителем существенных содержательных или дизайнерских решений.
- Не устанавливать движки и не начинать реализацию автоматически.

<a id="render"></a>
## 9. `omr-render` / `/omr-render`

**Вход:** требования, сценарий, необходимый контент и доступные ресурсы.
**Результат:** исходники выбранных движков, подготовленные медиа и `out/video.mp4`.

- Реализовать сценарий на выбранном движке или их комбинации.
- По необходимости подготовить окружение согласно разделу 10.
- Подобрать, скачать или сгенерировать конкретные ресурсы под сцены.
- Поддерживать предоставленные файлы, поиск внешних изображений, видеовставок,
  музыки и звуковых эффектов, а также генерацию ресурсов.
- Поддерживать готовую запись озвучки и генерацию речи по требованиям проекта.
- Отделять получение речи из текста от обработки готовых записей. Общий
  `omr-audio` на FFmpeg не зависит от модели/сервера и применяется также к записям
  человека. Обработка включает пробную склейку, уровни между репликами, внутреннюю
  динамику, каналы, сведение и проверку декодированного конечного файла на слух
  и измерениями. Недоступное прослушивание явно остаётся ограничением.
- Сохранять источники и сведения об условиях использования внешних ресурсов.
- Платные сервисы и недостающие доступы согласовывать с пользователем.
  При отсутствии нужного инструмента не заявлять, что ресурс создан.
- В гибридном режиме рендерить фрагменты Manim и собирать финальный ролик в Remotion.
- Выполнить проверки из раздела 11 и сообщить фактический путь к результату.

Это полный этап производства, а не только команда экспорта.

<a id="dependencies"></a>
## 10. Окружения и зависимости

- На этапах требований, контента и сценария заранее устанавливать движки не нужно.
- Remotion устанавливается локально только в Remotion- и гибридном проектах.
  Каждый такой проект имеет собственные зависимости и зафиксированные версии;
  он не должен зависеть от `node_modules` корня OMR или соседнего ролика.
- В чисто Manim-проекте не создавать Remotion, `package.json` и `node_modules`
  без отдельной реальной необходимости.
- На текущей машине Manim доступен через общее пользовательское окружение `uv tool`.
  Для обычных проектов используется это окружение; при особых Python-зависимостях
  или требованиях к версии — отдельное окружение проекта.
- Не менять общее окружение Manim ради одного ролика без согласования.
- Подключить официальный набор `remotion-dev/skills` как техническую зависимость,
  проверить нужный состав и фактическую загрузку.
- Для Manim использовать доступные `manim` и `manim-local` вместе; локальный скил
  описывает особенности этой машины. В переносимой установке проверять наличие
  окружения, не встраивать персональные абсолютные пути.
- Отсутствующие обязательные скилы или инструменты явно обозначать и согласовывать
  дальнейшие действия; не подменять их вымышленными возможностями.
- FFmpeg и FFprobe нужны как доступные CLI для проверки экспорта всех режимов,
  а при звуке — для анализа и сведения. Наличие встроенного бинарника видеодвижка
  не заменяет проверку PATH, фильтров и кодеков. Полный перечень с официальными
  ссылками установки — в `docs/dependencies.md`; TTS/ASR зависят от задания,
  конкретная модель не входит в обязательные зависимости OMR.

<a id="verification"></a>
## 11. Проверки и критерии готовности

### Готовность ролика

- Успешная сборка и рендер; проверены параметры и длительность итогового файла.
- Визуально проверены ключевые кадры и переходы: читаемость, компоновка,
  отсутствие обрезанных элементов и дефектов стыковки.
- Проверены наличие и синхронизация предусмотренного звука.
- Дефекты реализации исправляются самостоятельно. Изменения содержания или дизайна
  за пределами сценария обсуждаются с пользователем.
- Успешное кодирование не равно визуальной или звуковой проверке.
  Невыполненные проверки и ограничения инструментов указывать явно.

### Готовность скилов и команд

- Создавать каждый скил через `ris-port-op-author-skill`, загрузив его через `skill`.
- Проверить метаданные, ресурсы, зависимости, границы ответственности и ссылки.
- Проверить выбор на подходящих, соседних и нерелевантных запросах; выполнить
  небольшие репрезентативные проверки поведения по методу author-скила.
- Проверить обнаружение и вызов скила и соответствующей команды из подпапки ролика.
- Проверить соблюдение ручных переходов и поведение при недостаточных входах.
- Для производственного этапа проверить все три режима на коротких примерах.
- Различать просмотр инструкций, структурные проверки и наблюдаемое исполнение.
  Непроведённые проверки не объявлять успешными.
- Если обязательная проверка заблокирована, сохранить результат и точный блокер;
  не отмечать всю задачу завершённой.

<a id="installation"></a>
## 12. Установка и `AGENTS.md`

- Целевая установка OMR — локально в рабочей области, в `.opencode/`.
  Глобальная установка не требуется.
- README содержит блок для AI-агентов: что прочитать, куда установить скилы
  и команды, какие зависимости проверить, как дополнить `AGENTS.md` и как
  подтвердить работоспособность из подпапки ролика.
- При дополнении существующего `AGENTS.md` сохранять пользовательские инструкции.
- Правила должны охватывать три режима, структуру проектов, отложенную установку
  движков, использование профильных скилов, единый режим с контрольными точками
  и самостоятельный режим без автоматических переходов/ревью.
- Точный механизм получения набора, публичный URL и проверенные команды установки
  определяются при реализации. До этого README не должен выдавать их за готовые.
- Создание исходников скила и его установка — разные операции. В каждой сессии
  явно учитывать разрешённый объём работ; локальное подключение предусмотрено
  этим проектом, публикация выполняется отдельной задачей TODO.
